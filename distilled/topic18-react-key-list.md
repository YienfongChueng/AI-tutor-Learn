# 条件与列表渲染（key 的真实作用）

**它解决什么问题**
理解 key 决定 state 归属，而不是性能优化项。

**核心机制**
- 条件渲染即 JS：三元、&& 短路，无指令系统
- diff 只做同层比较，type+key 是身份判定依据
- key 变 -> 销毁重建 state 清零；key 稳 -> 复用 state 保留
- key 反向应用：换 key 强制重置组件
- 口诀：props 跟数据走，state 跟位置走

**最容易被追问的点**
- "index 作 key 头部插入会怎样？" -> ❤/草稿串到新数据上；旧数据的 state 丢失（跟位置不跟数据）
- "count && <X/> 的坑？" -> count=0 时 `0 && x` 求值为 0，页面渲染裸 "0"；写 `count > 0 &&`
- "想清空组件内部 state 怎么办？" -> 换 key（如 `key={userId}`），销毁重建
- "什么时候 index 可用？" -> 列表永不增删排序的静态场景
- "key 未指定会怎样？" -> 默认用位置 index，动态列表等于埋雷

**一句话类比**
key 是工位牌不是人名牌：换了人没换牌（index key），工资记录（state）就算到新人头上。
