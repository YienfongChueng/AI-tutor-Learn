# 3.3 数据请求与服务端状态（TanStack Query）

**它解决什么问题**
useEffect+useFetch 在真实项目里的三堵墙：重复请求、无缓存、样板无底洞。根因：服务端状态是"远端数据的本地快照"，用 useState 管它等于手搓缓存系统。

**核心机制**
- queryKey 是缓存身份证：影响结果的变量必须进 key
- key 变化 = 自动重新请求（全局作用域的 deps）
- 同 key 并发挂载自动去重合并成一次请求
- staleTime 保质期（过期仍可先显旧数据再后台刷）、gcTime 冷藏期（没人用后保留时长）
- invalidate 前缀匹配失效一整棵 key 子树
- queryFn 自带 AbortSignal，竞态内置

**最容易被追问的点**
- "userId 变了为啥还是旧数据？" -> key 写成 `['user']` 或 `['user','userId']`（字面量！）没进变量，缓存串台
- "失效流 vs 直写流怎么选？" -> 默认失效（服务器真相/不拼形状/只需知道什么变了）；直写只配乐观更新
- "切回页面看到什么？" -> 缓存 stale 未被 gc：秒出旧数据+后台刷新；被 gc：骨架屏重来
- "两个组件同 key 请求几次？" -> 一次，并发去重不是缓存命中
- "isPending 和 isFetching？" -> 前者从未拿到过数据，后者正在请求（含后台刷新）

**一句话类比**
queryKey 像快递单号：单号不同就是不同的包裹（各自请求）；两个人追同一个单号只派一趟车（去重）；包裹签收后放驿站（缓存）保 5 分钟（gcTime），过保质期（staleTime）再取就先给你旧的、同时联系卖家补发最新的。
